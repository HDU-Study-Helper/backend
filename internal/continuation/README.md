# Durable question continuation

`WithSource` is a Go host binding, not part of the run or tool JSON. The external application supplies the authenticated owner and stable conversation key for ChB. Background Filter, first-course and standalone Worker/Learner runs originate in ChA unless the host has already bound a source. Descendants inherit it unchanged. Chat cannot execute in a Workflow scope.

Only logical model-facing turns are archived (input, authorized evidence/memory, assistant calls, tool results, final output, validation feedback, and known staging receipt). No provider transport, internal reasoning, credentials configuration, executable tool handles, or previous system prompt is restored. Known secret-shaped values are masked; arbitrary free text is still private owner data. Restore checks owner, agent type/status, tool and permission revocation, and current Workflow availability/version. Historical turns are quoted in a user message; fresh system policy, time, Workflow, and staging baseline control each new run. Context limits still apply; history is not silently truncated.

- `PendingQuestions`: owner + channel + key. An empty key lists all ChA questions for the authenticated owner. Each pending row contains one server-generated question ID with type, text and options.
- `Answer`: requires the same trusted source. A database claim prevents concurrent execution. Identical completed answers return the stored result; changed answers and cancelled questions conflict. There is no inactivity expiry. If a process dies *after claiming* but before saving its result, the claim is deliberately not rerun: operations may already have committed, and operator reconciliation is necessary.
- ChA persists its silent question notice in the question transaction. A validated Learner `READY` may commit known work plus a remaining question atomically. `NEEDS_INFO` cannot discard staged changes. Unresolved questions resume the leaf first; a second blocking question keeps the ancestor chain suspended. Completed children return to the actual handled ancestors; no role inferred from user/model JSON. Only ChB reaches Chat.
- A new task in a ChB conversation cancels only pending questions in that conversation. It does not roll back work or affect any other channel. The Chat ingress serializes tasks and answer requests within a thread.
- `RunScheduledWorker` accepts an authenticated owner, originating Worker run ID, and business input. It resolves the archived Worker and Workflow, restores prior context, and starts a fresh asynchronous ChA source without waking the original parents. It does not set notification mode. A job cannot provide a transcript or select a different Worker through its arguments.

For passive run-control batches the stable item ID is the ChA source key. The archive carries a separate trusted owner/batch/item link; resumed runs and their artifacts are observed under the original item. A durable open question sets `NEEDS_USER_INPUT` before Filter format-repair or re-dispatch. Answering records the actual resumed run IDs and clears/replaces pending question IDs. A single root item becomes `COMPLETED` only with an observed completed Worker and matching completed Filter result; otherwise it remains `PARTIAL` or waiting. Historical batch/round status is not rewritten. The resumed model receives the host-issued `question_answer:<id>` reference to the authenticated answer, not an authority token.

The v18 SQL for this component is `continuationSchemaSQL`. Isolated PostgreSQL tests cover atomic staging/question/notice persistence, owner/source checks, retry and cancellation, service restart, ChA/ChB parent restoration and scheduled context reuse. No live account, notification delivery, or deployment is implied.
