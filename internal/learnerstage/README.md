# Learner staging host contract

`agent.Service.Run` routes Learner instances through a separate per-run Runtime. The reusable framework is unchanged. Real dispatch resolves the caller from trusted owner/agent identity: Filter may initialize without a Workflow binding; Worker may revise its bound Workflow. Explicit internal callers can use `agent.WithLearnerStage(ctx, owner, "INITIALIZE"|"REVISE", targetID)`; JSON cannot establish this authority.

The runtime reuses the host Providers, Resolver, Observer and optional WorkflowLocker. Workflow/Memory tools use a per-run repository overlay; data tools remain read-only through the existing backend bridge. No scheduling, platform collection, notification or child dispatch service is wired. `learner_stage_select` selects one owned target, and `learner_stage_state` returns session ID, target, baseline version and staging revision. `workflow_create` creates only an overlay target; then normal memory tools edit its private knowledge. Model-facing creation schema excludes legacy `initial_private_memories`; its atomic persistence receipt must not be mistaken for staging success.

Selected target reads include all PRI records, independent of Agent injection or memory validity. Search can request historical state; mutations are restricted to target PRI. Related private scopes are not readable through endpoints. Internal target relations are staged; existing user-PUB parents remain valid, while new cross-scope relation creation is not exposed in this minimum slice.

The final model object must match `learner_staging_v2`, session, path, selected entity, baseline and exact current revision. Host validation can request at most two corrections inside the same Run and staging session. Syntax/shape corrections have tools disabled for that response; recoverable semantic/state errors restore the original authorized tools and revalidate the final result. Cancellation, actual commit permission failures, storage conflicts and exhausted budgets do not trigger recovery. Model calls, tokens and correction attempts remain in the original Run audit; no failed final starts a second investigation automatically. Only READY/NO_CHANGE plus READY_TO_COMMIT reaches storage. Tool errors remain in the Run audit. An unrelated tool error (including an unknown tool or a denied call) does not veto a valid commit; the tool’s permission check still applies. Cancellation, invalid output, stale markers, and the existing conflict/budget checks still block submission. Initialization additionally requires an active specific Workflow and sourced private knowledge; no fixed number of dimensions, queries or memories is prescribed.

`dbbridge` v16 adds a durable per-owner/session commit ledger. A short transaction rechecks enabled Learner permissions and specific required tools, compares Workflow plus all target-memory/relation baseline, applies only differences, and records a receipt. Workflow version changes only when its definition/metadata changes. Unchanged memory timestamps and relation attribution survive. Commit replay with the identical payload returns its receipt, a changed payload conflicts. Lost acknowledgement is reconciled by reading that ledger. Returned model READY is converted after commit to existing APPLIED/NO_CHANGE management JSON plus `commit_receipt`; only then does Observer expose a successful final result to parent processing. The running Agent Run audit is persisted immediately; Session defers its provisional model terminal record, and Service saves exactly one final running-to-terminal transition after commit/validation. Timeout and cancellation finalize with an independent cleanup context and retain their original error code.

## Validation and limits

Focused tests cover complete versus malformed/missing/cancelled output, corrected/unresolved Schema errors, target PRI isolation, creation rollback, optimistic memory conflict, same-session idempotency, memory-only version stability, NO_CHANGE, archive/delete and delete receipt replay. Database tests require a dedicated TEST_DATABASE_URL and create isolated random schemas. No production database or teaching platform is used.

Uncommitted staging is currently memory resident, scoped to a Run; restart/resume across processes is not implemented. Idempotency is per staging session, not automatic request_id deduplication across new Runs. Fully specified platform_records references (dataset, central id, connection_id and external_id) are checked against the current owner's active authorized connection in the commit transaction, and inconsistent mappings reject the whole commit. Legacy strings, partial references and other datasets retain their format; this check does not prove the factual truth of the memory content. Provenance supplied by data service and higher-level evidence verification remain relevant. A Service-owned nonblocking gate shares Learner per-agent and total staging concurrency across temporary runtimes; provider request gates remain shared. The general non-Learner Runtime total counter remains separate. Parent Worker snapshot refresh after a committed definition revision remains a host continuation concern. Legacy runcontrol active-Workflow verification is not a deletion/archival consumer; callers needing those branches must consume commit_receipt status explicitly. The readonly aggregate memory list has existing API limits; target snapshot storage is bounded at commit (8 MiB), not paged in this first slice.
